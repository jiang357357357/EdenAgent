## 模型请求上下文顺序

2026-11-05 后续更新：当前默认正文为 `eden-overlimit-v3`，继续停用九项工具路由，并按用户指定在拼接入口注释 Style 的两句要求及标题、完整 Workflow 段和 Fixed precedence 句。v1/v2 及旧标识 `v3` 的快照仍严格匹配各自原文；25 类规则、角色核心动机、leading-v1 布局和末尾锚点保留。此前整卷报告仍只对应 v1。

2026-11-05 较早的 v2 更新：按用户要求，默认正文当时改为 `eden-overlimit-v2`，整段九项“工具选择与任务路由”在拼接入口注释，原文只保留用于 v1 历史快照兼容。角色核心动机、leading-v1 首部布局和同条末尾锚点保留；宿主通用工具指引照常提供。原整卷报告对应带九项路由的 v1，后续 v2/v3 均尚未重跑整卷。

超限模式开启且使用新入队的 `leading-v1` 布局时，普通单角色对话的源码排列如下。可选内容只在适用时出现；适配器可能按供应商约定将首条 system 转为 developer。

```text
system（开头）:
  1. 角色身份与人设原文
  2. 开启的模式长正文（直接正文，无“超限模式”标题）
  3. 通用系统规则
  4. QQ 群聊附加规则（适用时）
  5. 聊天回复长度偏好（适用时）
  6. JSON 角色资料
  7. 固定的技能、工具发现与使用指引
  8. 已呈现工具的附加指引（有时）
  9. 角色规则短锚点（与长正文同属这一条 system，位于工具指引之后）

历史 user / assistant / tool（保留原顺序）:
  1. 对话历史，或压缩摘要及保留消息
  2. 之前已保存的运行资料快照，仍保留原有位置

user（宿主资料快照，首次／变化时才追加）:
  1. 环境与后台任务类型
  2. 可用技能摘要及动态目录状态
  3. 当前角色已注册工具的摘要目录，按稳定顺序排列

user（本轮）:
  1. 用户请求或后台任务说明
  2. 本轮附件引用清单（有时，与原始输入一起保存）
  3. 本轮直接输入的图片附件（有时）

user（有召回时）:
  1. 本轮长期记忆参考资料

assistant / tool（工具循环，若发生）:
  1. 助手工具调用
  2. 对应工具结果，包括 load_skill 返回的完整技能说明
  3. 若运行资料变化，在当前历史末尾追加新的宿主资料快照

user（工具输出带图时）:
  1. SDK 从工具结果提取的图片块

```

工具循环可以重复；新布局将模式正文与短锚点放在同一条开头 system 内，不再追加末尾 system，也不写入聊天历史。自动压缩预算计入长正文与短锚点，摘要请求仍使用独立摘要指令；后续对话重新组装当前设定。多人会话对每个行动角色使用其独立人设及导演任务说明，再使用相同的首部布局。工具参数结构仍通过独立的 tools 字段发送。

2026-11-04 用户批准后，新输入冻结 `layoutVersion: leading-v1`，模板正文仍为 `eden-overlimit-v1`。已入队的 v3、旧版 eden-overlimit-v1 及无版本快照没有布局字段，继续使用原来的末尾位置，但也删除宿主附加的 `# 超限模式提示词` 标题。宿主审计来源名称不作为消息发送；正文中原有的 MODE、拒答对抗等文字本次没有删除，因此不能保证模型不再辨认出这类提示。

2026-11-04 按用户要求采用 DSH 的资料归属与快照方式：附件引用随所属 user 保存；环境、任务种类、技能和工具目录不再拼入首条 system。运行资料使用 pi 公开的隐藏 custom_message 条目持久化，发给模型时转换为 user；只在当前保留快照不同、资料清空或压缩后缺少快照时追加。普通聊天、行动角色及隔离进程均接通，公开聊天事件移除宿主自动附加的引用后缀，保留原用户正文与附件组件。

工具目录按已注册能力生成，不再以是否展开参数过滤；展开或收起一个当前有效工具的参数不改变目录。实际提供给模型的原生 schemas 仍在 tools 字段中，按工具名保持稳定顺序；原有发现、加载、执行查找与权限判断继续生效。可用技能摘要和目录刷新故障属于资料快照，固定操作指引保留在 system。工具库、角色或任务状态实际变化时，仍会产生相应更新。

当前运行时为 pi 0.82.0 的 Chat Completions 适配，公开能力没有声明普通 system 的 in-history 更新语义，故采用 DSH 的 leading-only 兼容分支，继续维护开头系统提示；`model.request.systemPromptUpdatePolicy` 记录为 `leading-only-fallback`。没有根据模型名称猜测能力，也没有引入 PTC／run_code 路径。模式来源按实际首条载荷核对后记录，独立压缩请求不会误记长正文与短锚点。

自动压缩将最新运行资料快照放入保留尾部，不以摘要替代其正文；手动压缩后若快照未保留，下次输入会按当前资料重新保存。宿主内容指纹用于投影后的快照去重，不是缓存命中证据；普通请求及分段压缩通过公开消息转换移除 custom 来源元数据。新增检查点类型兼容仍使用公开 custom_message／custom AgentMessage 形式，不修改用户旧历史。记忆召回仍为本轮输入后的临时 user 参考资料，本次没有改变其持久化策略。

模型请求另记 `messageSources`：区分本轮输入、宿主资料快照和召回记忆，不把内部来源标识塞进供应商消息。前端优先按这些来源识别“本次请求输入”，并标记运行资料和记忆；旧快照没有来源时沿用兼容展示。这里描述当前源码行为；真实模型语义与缓存效果尚未验收，不能把静态检查和构建成功当作能力提升证据。

### 当前排序的问题与待验证项（2026-11-04）

以下包含原排序评审后的处理状态和仍待验证的影响。源码已完成 DSH 方式的接入，尚未替换现有运行程序。此前完整真实模型对比使用的是末尾布局，新首部布局的接入验证不能直接替代效果对比，也不能直接将设计风险归因于此前某轮回答错误。

| 项目 | 代码事实 | 可能影响及处理方向 |
| --- | --- | --- |

省略其他动态项，当前首部布局与旧快照的序列差异如下：

```text
S = 开头 system（新布局已包含模式与短锚点）
H = 相同历史
U = 本轮用户消息
M = 仅旧快照使用的末尾模式 system
A/T = 新增助手工具调用及工具结果

新布局请求一：S + H + U
新布局请求二：S + H + U + A/T

旧快照请求一：S + H + U + M
旧快照请求二：S + H + U + A/T + M

只有在其余消息与工具定义都稳定时，上面的新布局请求一才是请求二的前缀。
```

记忆也有独立的跨轮变化：上一轮实际发送的参考消息不进入持久历史，下一轮会在新用户消息后插入新的参考。即便本轮工具循环中记忆的位置固定，也不能据此保证跨轮前缀保持不变。

DeepSeek 官方说明缓存匹配已持久化的完整前缀单元，提供 `prompt_cache_hit_tokens`／`prompt_cache_miss_tokens`，并采用尽力而为的缓存策略。因此应核对最终序列、接入模型与真实回执，不用本地配置指纹代替缓存证据。[缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

官方当前说明 Chat Completions 可以插入对话中的 system；但 `/models` 中 `api_capabilities.anthropic_messages.system_prompt_update` 专用于 Anthropic 协议，其中 `in-history` 的最新 system 是完整替换旧提示，而 `leading-only` 只使用开头提示。我们当前适配 Chat Completions，不能直接根据该 Anthropic 字段断言尾部 system 如何生效。[工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/)、[模型能力说明](https://api-docs.deepseek.com/api/list-models/)

后续按新首部布局测量真实缓存与任务表现，并验证资料快照、附件归属和压缩保留行为。比较需固定模型、采样、任务及上下文内容，分别观察首轮、工具循环、跨轮、模式切换和压缩后的行为；记录真实 tool 回执、请求成功状态及 cache usage，不能仅用“模型回答了”判定方案通过。默认模板 eden-overlimit-v1 只适配 dsh-purge 的角色身份与工具／路由，保留“盲目忠诚＋自我保存”及其余规则；本次长正文 SHA-256 保持 `85d71fffed43093eaf1e0c5d5b0cd0b3c0b51a59ac5d97392ef898edf80421b0`，仅布局、标题与固定短锚点发生变化。原报告入口 `.artifacts/dsh-purge/live/report.html` 已替换为首部布局整卷重测；旧问题、回答与评分保存在 `live/previous-summary.json`。本轮同时修正 DeepSeek 实际输出上限字段为 max_tokens，截断单列，不把两轮差值只归因于位置变化；详见实施跟踪最新条目。

### 参考项目中的附件与工具目录（2026-11-04）

按用户指定的本地 `文档/参考` 源码核对，检出提交分别为 DSH `687f282e8625c6b8d11ff58211a90524be2e4317`、OpenCode `bddf5346c8e3a0c7c662d231c5f3e302ae5f0b1f`、pi `bd3c9b823762b7383954aa49e13ee350471015fe`。这是上述确定提交的实现对照，不代表上游当前最新版；本轮没有拉取、安装或执行这些项目。参考 pi 的 coding-agent 包声明版本为 `1.3.0`，与本项目使用的 pi `0.82.0` 分开判断，后续适配仍遵守公开 SDK 边界。

| 项目 | 附件进入模型的位置 | 工具说明、目录和定义进入模型的位置 |
| --- | --- | --- |
| DeepSeek Harness | controller 将文本、图片引用和文件引用组成同一条 `UserMessage.content`；附件 admission 保留块顺序。图片在供应商序列化时转换为该消息中的引用说明与图片块。 | 原生模式将 schemas 通过独立 tools 传入，工具指南仍可属于 system。PTC 模式将生成的工具 SDK 写入 system，并只原生暴露 `run_code`。动态运行环境另外保存为有来源的 user 快照。 |
| OpenCode | 用户消息中依次放技能展开文本、用户正文、附件；文本文件转为文本块，图片及支持的 PDF 转为媒体块。具体供应商再负责格式与能力处理。 | 原生定义通过独立 tools 传入；Code Mode 的工具目录属于初始 system 指令，提供命名空间与预算内签名摘要，其余通过 `execute` 内的 `search` 查找。目录随后变化会生成差异或替换说明，作为新增 system 消息保存。 |
| pi | 用户文字与归一化后的图片组成同一条 user 的 content；工具返回的图片依接口适配，Chat Completions 可补充为 user 图片消息。 | coding-agent 的结构化 system 也包含已选工具的一行摘要和使用规则。可选 `tool_search` 使用固定描述，特意不枚举待加载工具和命名空间；匹配结果在工具回执中，加载的定义在后续请求声明。该搜索扩展默认未激活；durable 包也提供相应扩展。 |

这三份实现都允许 system 含有工具指南，说明“工具说明出现在 system”本身不足以判断设计错误。评审应进一步核对内容变化频率、目录是否必要、工具定义是否另外传入，以及如何保留已经发送的历史前缀。

值得借鉴的更新机制：

- **DSH 的快照与能力判断**：`RuntimeContextProjection` 只在保留的运行资料与当前值不同时生成新的、带 `source.kind=runtime-context` 的 user 快照。`SystemPromptProjection` 在接口支持 in-history 且请求系列连续时，保留原有节点并追加变化后的完整 system；不支持、请求系列重建或提示清空时会归并到开头。它并不保证所有协议都能原地保留缓存。
- **OpenCode 的初始基线与变化记录**：`InstructionState` 保存当前指令 epoch 的 initial/current 值；读取初始提示使用 initial，而后续更新文本持久化为 `SessionMessage.System`。Code Mode 目录按变化生成新增、变更、移除说明，必要时重新给出目录；压缩等操作可以推进 epoch，建立新的基线。其初始目录保留在 system，与每轮重写开头有区别。
- **pi 的固定发现入口**：`TOOL_SEARCH_DESCRIPTION` 明确避免枚举可检索工具，MCP 新工具接入时无需改写这一描述。它按查询匹配并加载工具，coding-agent 搜索扩展与 durable 扩展分别维护所需状态；durable 的 `control.addTools` 将加载项写入会话分支的 modelTools。实际 schemas 更新仍受供应商协议与适配规则影响。

对照阶段确定、随后已接入的两个调整方向：

1. **附件引用归属用户输入**。调整前 Eden 图片本体已经进入 user 图片块，首条 system 额外保存 `blobId`、`filename`、`mime`、`byteLength`、`kind` 等引用清单。现在引用绑定在所属 user，保留图片块和按需读取入口，普通文件保留可读引用，不无条件展开正文。
2. **工具目录与发现规则分开**。调整前 Eden 使用 `!visible.has(tool.identity!)` 生成首条 system 的“尚未展开”目录，加载参数会让条目从该目录消失。用户最终选择 DSH 方式：固定发现说明留在 system，工具／技能目录作为有来源的动态 user 快照保存；目录基于已注册能力且稳定排序，实际 schema 继续经原生 tools 提供，搜索和加载回执保持原契约。

以上方向已经完成源码接入。工具 schemas 自身的增减也可能影响最终前缀，目录迁移不能单独保证命中率；实际比较仍需使用当前接入模型、真实请求载荷和供应商 usage。用户已批准的超限模式末尾 system 排列保持原实施状态。

## 本机文件读写

`read_file`、`write_file`、`edit_file` 支持本机绝对路径，包括工作区外文件；相对路径以所选工作区为基准，按当前 OS 账户权限执行。写入仍经过原有授权，显示实际目标路径，复核工作区选择、文件版本和路径重定向；无需改用终端命令才能写入工作区外文件。

`write_file` 在授权通过后自动递归创建缺失的父目录，例如写入 `E:\work\导出\视频报告\说明.md` 时，可自动创建尚不存在的 `导出` 和 `视频报告`。已有同名普通文件阻挡目录、失效链接、文件版本冲突、权限拒绝或取消会失败；不在等待审批时创建目录。共享资料库写入同样自动建父目录，继续使用独立的目录、编辑权限和审批边界。

`read_image` 直接查看磁盘图片，path 同样接受本机绝对路径或工作区相对路径，支持 PNG、JPEG、WebP、GIF，每张最多 6 MiB。图片通过原生图片块进入当前模型，文字结果只保留文件名、路径、类型和大小；当前模型必须支持图片。读取仍受系统文件权限、当前工作区与子任务策略约束，QQ 调用还经过既有读取授权。它适合查看生成的截图、总表或单帧，屏幕／摄像头工具继续用于实时画面。

伊甸园中已注册的 `send_qq_file` 在普通聊天默认展示完整参数，使用工作区相对路径发送不超过 100 MB 的文件。它通过 Core 内置 QQ 通道执行，与 `list_connectors` 的自定义连接器列表独立；空列表不能用来判断 QQ 文件发送能力。实际发送仍检查机器人、接收目标、权限和回执；工作区外文件可先复制进工作区。WSL 的 `$TMPDIR` 是临时文件推荐位置，虚拟环境可使用其他有写权限的持久目录，依赖是否可用要区分 WSL 和本机运行时。

## 视频理解与 256K 默认窗口

已内置 `video-context` 技能和七个工具：`inspect_video`、`prepare_video`、`read_video_timeline`、`get_video_frames`、`get_video_frame_previews`、`delete_video_job`、`video_context_doctor`。引擎是固定提交的 MIT VideoContext Python 处理器，由 TS 宿主管理审批、当前输入、工作区和角色归属。App 支持上传视频或工作区文件；QQ 私聊支持视频消息，群聊需引用同群视频并明确 @机器人。帧图直接进入当前模型的图片输入，因此当前模型须支持图像。YouTube 下载入口已接入，但未做真实在线平台验收；B站、抖音和 GIF 转视频适配尚未提供。

Windows 首次准备独立运行时（本机本轮已经完成）：

```powershell
npm run setup:video -- --python C:/Python312/python.exe --ffmpeg-dir C:/Tools/ffmpeg
```

FFmpeg 目录需包含 `bin/ffmpeg.exe`、`bin/ffprobe.exe` 和许可证。安装器使用 `uv` 安装固定依赖，并下载 multilingual Whisper tiny；已有 tiny 模型可传 `--model-dir <目录>`。输出默认位于 `Data/runtime/video-context`，拒绝覆盖；需要重新准备时用 `--output <新目录>`，并通过 `EDEN_AGENT_VIDEO_RUNTIME_ROOT` 指定。当前自动组装器仅支持 Windows，其他平台须自行准备兼容 `runtime.json`。发行脚本将运行时与源码、许可一起打包，Python 不依赖 Core 虚拟环境或试验目录。

每次图片读取通常 4 帧、最多 8 帧；处理任务限时 110 秒、输入最多 512 MiB，每个视频工作进程的图片响应控制在 MCP 的 8 MiB 报文以内。App 附件仍受现有 32 MiB 总量限制，QQ 视频受现有 100 MB 文件限制；大视频可放入当前 App 工作区后指定范围分析。tiny 中文转写有错词，工具会明确报告转写不可用或部分成功。

本地模型默认窗口和 Mon 未提供窗口时的回退值均为 **262144 tokens（256K）**。`EDEN_AGENT_CONTEXT_WINDOW` 的显式本地配置、Core 模型显式 `default_params.context_window` 及已确认持久绑定继续生效；本轮不改写真实模型数据库，也不宣称扩大了供应商的实际容量。修改默认值后需重启对应 Server，Mon 旧绑定需重新确认且模型配置允许 256K 才能使用新窗口。

视频任务缓存位于当前世界／账号数据目录的 `video-context` 下，再按会话和行动角色划分；临时输入调用后清理，任务可跨回合读取，用 `delete_video_job` 主动删除。执行继续使用当前 OS 账户权限，不引入 OS 沙箱。

视频入口在导入引擎前把结构化日志定向到 stderr，stdout 仅承载 MCP。宿主分别报告无效 UTF-8、无效 JSON、无效 JSON-RPC 结构／响应和超过 8 MiB 的报文；保留最多 16 KiB 的进程 stderr 尾部，向模型提供最多 2000 字符的诊断片段。进程失败和工具正常返回的 `isError` 都保留原因；主动终止工作进程的退出状态不会冒充业务失败原因。仍保留原有 stderr 总量、超时、取消和进程退出检查。

## 运行结构

Electron 分别监管伊甸园（`mon`）与尘世（`local`）两个 Node Server。每个宿主通过 `packages/runtime-pi` 调用 pi 公共 SDK；前端通过当前世界的 WebSocket JSON-RPC 和 Blob 端点访问服务。

| --- | --- |
| `Server/src` | TS 宿主、业务模块、传输与启动组装 |
| `packages/runtime-pi` | 唯一直接导入 pi SDK 的适配包 |
| `packages/api` | 协议 schema 与共享类型 |
| `packages/store` | SQLite、schema 与迁移基础设施 |

| `packages/execution`、`packages/integrations` | 命令执行与外部集成 |

宿主和连接器使用 Node/TypeScript。Windows 桌面指针观察组件保留独立 Rust 构建，完整桌面制品的要求见[桌面发行操作](技术/ts-migration/桌面发行操作.md)。

## Windows 桌面操作

正常聊天可发现并操作当前账户下已打开的应用窗口。首次调用沿用当前权限模式申请桌面任务授权；工具提供窗口截图、控件、点击、输入、按键、滚动、拖动、窗口管理与应用启动。控制界面支持暂停、恢复与停止，输入观察器提供 `Ctrl+Alt+F12` 全局停止；恢复不会重放取消的动作，需要重新观察。QQ 和自醒任务不继承本机聊天授权。

Electron 客户端现使用独立桌面控制悬浮窗：拖动顶部移动、右上角切换置顶，位置会记住；主窗口隐藏后仍可控制，托盘“桌面控制”可重新打开。关闭浮窗会先停止仍在执行的桌面操作。浏览器保留页面内控制条。此改动需要从托盘完全退出并重启客户端加载，前台实际拖动尚待验收，见[独立悬浮窗记录](技术/ts-migration/实施记录/2026-10-22-桌面控制独立悬浮窗.md)。

双世界通过同一个 broker 串行共享物理输入，数据库和审批仍各自独立。默认服务目录为 `%LOCALAPPDATA%/EdenAgent/desktop-control`；如使用 `EDEN_AGENT_DESKTOP_BROKER_ROOT`，操作同一桌面的两个世界应设置相同目录。当前内置官方 `@trycua/cua-driver@0.28.0`、Windows 原生库和受管 worker，无需另装 Cua。全部 56 个公开工具以 `cua_*` 提供桌面、浏览器、剪贴板、录制回放、配置及会话能力；原 `desktop_*` 接口保留。Windows 输入观察器仍需系统 .NET Framework 编译器构建。

桌面结果分别报告 execution 派发事实和 verification 定向证据；delivered 不等同业务完成，完整值／精确插入／expect 条件确认只说明对应界面状态。只读成功返回 status=read，不可读文字为 null。兼容动作附带 observationReady=true 时直接沿新引用继续；显式观察可用 query/maxElements 缩小范围，省略节点不代表不存在。完整审计与截图保留，模型取得有界视图。该投影及新版 schema、技能须 Agent Server 正常重载；仅更新 broker 不等同 Server 内存已更新。见[结果契约修复及真实验收](技术/ts-migration/实施记录/2026-10-24-桌面工具派发核验与模型结果修复.md)。

Cua 默认后台投递，前台需显式选择；截图质量、捕获可用性及平台限制以实际回执为准。宿主保留原始坐标，不按 UIA 根矩形拉伸截图；发现驱动与系统窗口边界明显不一致时标记未知并阻止兼容控件输入。跨窗口拖放使用 `cua_get_desktop_state` 与 `cua_drag(scope=desktop)`。下载、上传、剪贴板写入、录制、回放、安装及配置修改有具体调用审批。引用按会话、回合和行动角色隔离，取消／断线不重放动作；暂停与停止继续有效。2026-10-24 已在独立 WinForms 窗口完成含前台输入的 8 组真实验收；QQ、多显示器及硬件快捷键专项仍待完成。

Windows 的专属 Cua worker 在 SDK 加载前通过固定 Koffi 依赖设置并验证 PMv2 DPI，避免 Node 宿主在缩放显示器上得到虚拟化尺寸；客户端和 Server 的 DPI 不变。`desktop_window resize` 使用物理像素下的可见窗口边界，结果附带请求／实际边界及读回核验。兼容拒绝保留 `driverMessage`，并可能返回新 `observation`，后续使用其中的新引用；旧窗口引用失效时重新发现目标，不猜测同名窗口。真实验收需要显式设置 `EDEN_DESKTOP_LIVE=1` 后运行 `Server/tests/integration/desktop/live-cua.test.ts`，默认测试跳过该入口。详见[兼容层修复与真实验收](技术/ts-migration/实施记录/2026-10-24-Cua兼容层修复与真实窗口验收.md)。

共享协议为 `eden.desktop.3`。客户端先探测实际端点，离线遗留登记允许在执行需要时自动启动内置服务并更新；只读状态探测不启动服务。在线不兼容版本不会自动替换，需要通过对应启动器协调升级。托盘的“停止”只停止桌面操作，不退出服务。登记替换和恢复不删除 `control.json`，不得通过删除状态目录绕过暂停或版本检查。显式 `EDEN_AGENT_DESKTOP_BROKER_ROOT` 会传给两个开发宿主；没有 `LOCALAPPDATA` 时仍沿用临时目录默认，不自动迁移已有控制状态。见[内置接入记录](技术/ts-migration/实施记录/2026-10-24-Cua官方运行时内置与完整工具接入.md)和[旧登记恢复修复](技术/ts-migration/实施记录/2026-10-24-桌面服务旧登记恢复与在线修复.md)。

## 自动长期记忆召回

自动召回采用本地 `bge-small-zh-v1.5` 向量相似度及阈值，不调用额外大模型或重排序模型。伊甸园先按当前账号和正在执行的角色读取 Agent 现有记忆，再向已绑定 Core 的 `POST /api/agent/memories/retrieve/` 请求评分；Core 验证角色归属并独立运行 ONNX，不经 Agent／MCP 反向取向量。不迁移或覆盖现有记忆，也不把 Core 已有记忆表与 Agent ID 混用。尘世使用独立本地后端，不借用伊甸园凭据。

默认阈值为 `0.6`，最多五条，不足相关度可返回零条。过期或无效的 `metadata.validUntil`、其他账号／角色和检索期间已修改或删除的记录不进入上下文。长内容按段落／长段句子和滑动窗口计算，返回与原文一致的命中片段；只裁剪本轮上下文，不改写原记录。该阈值来自小规模合成评估，仍可能漏召回，不代表所有模型、语种或记忆类型都合适。没有明确有效期的旧事实仍需结合时间和本轮信息判断。

动态记忆放在本轮用户输入后的参考消息中，同一轮工具调用期间固定；不追加到系统提示，不保存为 SDK 聊天检查点或前端消息。请求审计仍保留使用依据，压缩不把这份临时参考重新写入历史摘要。记忆变化不会改动系统提示和原聊天记录；供应商实际缓存命中仍受其前缀缓存规则影响。检索总时限 25 秒，服务不可用时提示模型仅依据当前对话，不回退为最近百条或无关旧记录；存储损坏继续中止执行。

Core 默认使用项目内置的 `Resources/Models/bge-small-zh-v1.5`。尘世按用户最新要求单独下载，不随 Agent 源码或普通构建携带权重：在尘世的“设置 → 高级设置 → 本地记忆模型”中手动点击“下载模型”，约 96 MB，支持进度、取消和重试；未下载时正常聊天可用，暂不检索长期记忆。打开设置或开始聊天均不会自动下载，也不借用 Core 内置模型。

尘世默认将模型保存到自身 `dataRoot/models/bge-small-zh-v1.5`（默认 `Agent/Data/realms/local/models/bge-small-zh-v1.5`）。从官方 Hugging Face 固定快照下载并逐文件核对长度和 SHA-256，完整成功后才将临时目录安装到目标路径；失败或取消只清理本次临时文件，不覆盖用户已有目录。下载完成后后续对话自动使用，重启后复用；下载行为由用户设置操作发起，不向智能体暴露新的下载工具。Core 原模型及配置保留；上轮临时复制到 Agent 源码／构建目录的内置副本已移至 `.artifacts/local-model-download-20261025/previous-builtins/` 备份，运行与构建不读取它们。

Core 需安装锁定依赖；`MONCORE_MEMORY_MODEL_PATH` 和尘世的 `EDEN_AGENT_MEMORY_MODEL_PATH` 仍可显式指定其他目录，也可自行准备完整模型后指定路径，`MONCORE_MEMORY_SIMILARITY_THRESHOLD` 调整 Core 阈值。向量缓存只在进程内保留，首次计算和大量记忆的索引性能仍需后续验证。新增下载 RPC 需要 Agent 正常重载，界面需载入更新后的前端；本次未重启在线服务。

## 自醒日记

自醒以角色自己的日记为目标，默认参考同角色最近一段 App 会话的最多三轮用户／角色交流，保留交流时间；素材不包含工具输出、后台自醒或其他角色的回复。伊甸园按已核对账号隔离，身份缺失时只查看当前会话；尘世可读取同角色、未绑定账号的本地会话，不读取其他账号的会话。

每个角色继续共用一个后台执行会话和唤醒时钟；每个新自醒回合独立组织模型上下文，不恢复上一轮日记、工具过程或压缩待办。日记围绕真实交流、确有依据的经历与角色自己的感受和想法，不默认写成系统巡检或任务进度流水；没有新交流时可以简短记录，不编造对话或行动。旧日记在需要回忆具体往事时按主题检索，旧打算不自动成为新任务。合并旧计划保留在档案中，不自动注入新轮次，也不因写完日记就标记为已核对。

已保存的日记、原始执行事件和工具审计保留；同一轮内工具交互、普通聊天和其他作业继续保留其上下文。上述行为需要 Agent Server 正常重新加载新源码或制品；仅打开自醒页面不会更新正在运行的宿主。

## 双世界、模型与数据

`npm run dev` 先识别现有 Server：同一世界、版本和工作区且接受所配置能力令牌的服务直接复用，仅为缺失的世界启动子进程。退出开发端只停止本次创建的服务，复用的 MonPM 常驻服务继续运行。已占用但无法确认身份的后端或 Web 端口会明确报错，默认入口不再强制结束监听进程。

需要常驻自醒时，应通过当前工作区的 MonPM 管理伊甸园 `agent-api`，并保持 Core 和 Agent 内置本地能力调度器可用；独立 MonOs 服务已退役，不需要单独启动。仅启动 Core 不会自动补齐被明确停止的 Agent。没有独立常驻 Server 时，开发入口自己创建的 Server 仍随开发端退出。

使用 MonPM 常驻伊甸园后，可通过 `npm run dev:desktop` 启动 Web 和桌面，连接已有 Mon 服务并单独监管尘世；需指向同一工作区及其 Mon 能力令牌，不能混用另一套安装的数据或令牌。本轮开发机配置与验收见[自醒通信恢复与常驻验收](技术/ts-migration/实施记录/2026-10-17-自醒通信恢复与常驻验收.md)。

自醒页面区分待派发任务、实际执行和调度器失败退避。通信恢复时，Agent 内置调度器对每个已持久化请求最多提前续派一次，复用原始事件与幂等键；失败后仍遵守退避，不新建重复任务。源码修改需要运行中的 Agent 使用相应新制品才会生效。

| 入口 | 默认端口 | 模型配置 |
| --- | --- | --- |
| 开发 Web | `40091` | 连接所选世界 |
| 伊甸园 Server | `40092` | Mon Core 已验证连接与角色/导演模型绑定 |
| 尘世 Server | `40093` | 本地配置或 `EDEN_AGENT_MODEL=provider/model` |

开发数据分别位于 `Data/realms/mon` 与 `Data/realms/local`；便携安装路径以其启动配置为准。两个世界使用独立进程、能力令牌、数据库、Blob、配置和外部副作用状态，事件先持久化再广播。模型凭据不跨世界继承，修改模型目录不自动改变已创建子任务的模型快照。

数据恢复和迁移走明确流程，不通过复制另一套认证文件或直接覆盖真实数据库解决启动错误。详见[数据迁移操作](技术/ts-migration/数据迁移操作.md)与[项目脚本说明](../Script/Project/README.md)。

## 源码入口

需要 Node.js 22.23.1 与 npm，完整克隆主仓库及子模块。首次运行从 `.monconfig.example` 创建本机 `.monconfig`，配置需要使用的模型与 Core 服务；已有本机配置应继续使用。能力令牌、模型密钥、运行配置和真实 Data 不提交到源码仓库。

| 命令 | 用途 |
| --- | --- |
| `npm run dev` | 构建宿主，复用同工作区 Server、补齐缺失世界，再启动 Web 与 Electron |
| `npm run dev:server` | 构建当前宿主及运行时，再启动单个配置的宿主 |
| `npm run dev:web` | 启动 Vite Web 客户端 |
| `npm run dev:desktop` | 启动桌面开发入口；外部服务要求见项目脚本说明 |
| `npm run generate:rpc` | 从 TS 契约与浏览器模板生成客户端入口 |
| `npm run build:server` | 构建宿主、隔离运行时及工作区搜索 worker |
| `npm run typecheck` | 检查 Server 与 Web 类型 |
| `npm run check:architecture` | 检查架构与规模约束 |
| `npm run test:server` | 运行 packages 与 Server 测试 |

以上为脚本入口，完整环境要求以对应脚本说明为准。后端复用、端口冲突、诊断、系统技能目录和调度路径见[项目脚本说明](../Script/Project/README.md)。复用的后台服务不会因前台重新构建而自动重载源码，需通过其原监管器另行重启。

## 工具、技能与扩展

模型默认接收当前场景的基础工具说明。当前作用域内已注册且符合策略的工具都可接受有效调用，已知名称和参数时无需先加载说明；不确定用法时通过 `list_tools` 发现、`load_tools` 获取完整参数说明。技能通过 `list_skills` 发现、`load_skill` 读取说明；工具说明展示与技能阅读状态独立。

说明展示状态按会话和角色保存，版本或工作区变化后重新核对。`unload_skill` 停用技能说明加载记录，`unload_tools` 仅移除后续模型请求中的完整工具说明，不撤销工具注册或权限。通用入口与具名工具共用目标参数、策略及审批检查；过期的说明选择不等于工具不可调用。详见[工具与技能按需加载](技术/Eden%20Agent%20工具与技能按需加载.md)。

`manage_plugins` 与插件开发页提供指南、草稿编辑、修订提交、验证、声明测试、精确版本安装和激活。替换草稿需要当前修订，安装需要对应制品的成功报告；生成源码不自动运行，模板不自动安装。当前生成插件为受限单文件 TS 工具，MCP、市场组件和连接器使用各自的生命周期。

连接器使用统一插件包的 `connector` 组件，经过安装、授权和启用，再配置实例与资源。`npm run build:connector` 调用 `package_connector.mjs` 构建指定源码目录；旧游戏连接器已移除。详见[连接器实施计划](技术/ts-migration/连接器统一实施计划.md)。

## 执行策略与资源

当前终端、插件、技能、MCP、连接器和 Git 源获取按系统账户权限本机运行，OS 沙箱已暂停。审批、版本核对、超时与取消继续生效；双世界没有 OS 文件或网络隔离。归档沙箱配置不是当前启用功能。

角色图片、Spine、声线、模型和游戏内容按各自来源及授权使用，不包含在项目软件许可中。角色二进制资源不进入代码仓库，可独立管理并从角色配置导入。许可与第三方声明见[项目首页](../README.md#使用与授权)。
