## B5：ESP32 设备控制桥（后端闭环已实现）

- 正常 Mon 会话新增 `list_esp32_devices`、`control_esp32_device` 与 `get_esp32_command_status`，分别完成设备发现、受控命令下发与结果查询；控制动作申请 `device.control` 审批，设备读取申请 `device.read` 审批，三项工具均限制为根智能体使用。
- Agent 通过已验证的会话 Core 连接访问 `/api/agent/devices/esp32/`，只使用用户拥有的数据库设备 ID；设备硬件标识、认证密钥与会话令牌不进入模型上下文。
- Core migration `Esp32.0005` 新增命令账本，记录 requestId、动作、参数、TTL 和 accepted/succeeded/failed/timed_out 状态；相同用户 requestId 幂等复用，不同载荷冲突时拒绝。
- Core 在下发前同时校验设备归属、控制动作白名单、设备声明能力、有效会话和新鲜心跳；查询或下发会关闭已过期/陈旧会话，修复数据库长期保留假 online 的问题。
- 服务端使用命令 UUID 作为 v2 req ID；设备 ACK/ERR 通过 ack_id 更新命令结果。现有设备固件需实现并声明 `control.*` 能力后才能执行对应动作，旧 `display.claim.text`、`audio.playback` 与 `call.assistant` 能力不会被误当成主动控制能力。
- Django 模型检查和 migration 一致性检查通过，`Esp32.0005` 已应用；Core ESP32 全部 44 项测试通过。Agent 类型检查、8 项定向工具测试和 Server 构建通过；测试没有向真实设备下发命令。
- 当前仓库不包含 ESP32 固件源码；现有设备只声明旧的显示、播放和通话能力，重新联网后仍需升级固件以处理 Agent 控制请求、回传 ACK/ERR 并声明对应 `control.*` 能力，Core 才会允许实际控制。

## B5：Agent 发起 ESP32 来电（服务端已实现并测试）

- `call.start` 不再与设备主动拨号的 `call.start` 混用；Agent 工具保持对外动作名，Core 下行协议改为 `call.incoming`，并要求固件声明 `control.call.incoming`。
- Agent Server 从当前会话参与者注入 Core Assistant ID；Core 重新校验用户、Assistant、角色、世界、设备归属、在线心跳和能力，不信任模型传入的身份。
- Core migration `Esp32.0006` 新增来电生命周期账本，状态为 pending/ringing/accepted/active/declined/missed/ended/failed；同一设备不允许重叠来电。
- 设备 ACK `call.incoming` 只表示已响铃；用户必须通过设备发送 `call.accept`，Core 才创建日常聊天 CallSession 并进入原 STT → CallChatService → TTS 链路。`call.decline` 仅记录拒接，不创建聊天会话。
- Agent 命令查询只公开来电状态和时间，不公开 CallSession ID、语音、STT 转录或聊天正文，保持 Agent 与 Core 日常聊天的隔离。
- 设备 WebSocket 重新连接时会结束上一连接遗留的邀请和 Core CallSession，避免异常中断后永久占线。
- Core migration 一致性检查、Django system check、ESP 完整 48 项测试通过；Agent Server 类型检查、9 项定向测试和构建通过。测试未向真实设备下发命令。
