# 自醒通信恢复与常驻验收（2026-10-17）

用户要求完成修复并进行真实测试。本记录针对当前开发机截图中“已提交计划，等待派发”的故障，不代表客户安装包或全部迁移业务已验收。所有时间除 ISO 字段外均为 Asia/Shanghai。

## 问题与修复

原 08:00 作业尚未产生输入或运行，MonOs 对同一持久提交累计 5 次通信失败并退避至 16:23。MonPM 的 agent-api 明确停止，Agent 依赖临时 npm 开发进程；后者退出时会连同 Server 停止。Agent 恢复可达后，旧调度器没有退避期间探测续派；Server 又把旧 queued 作业覆盖到 MonOs retrying 之上，页面因此缺少真实的重试时间和错误信息。旧 reqwest 外层错误不足以区分当时连接拒绝与超时，不能进一步倒推历史网络原因。

- Server `execution-schedule.ts` 按真实执行状态合并计划：已有输入、正在运行和结果未知优先；未接纳的旧排队作业不覆盖调度器退避或未来计划。暂停与修订待确认保持独立状态。
- Web `SelfAwakeControl.tsx` 显示 retrying 的失败详情，沿用原有重试时间、开关确认和不确定更新保护。
- MonOs `agent_transport.rs` 保存固定错误分类及可取得的系统错误码，不保存请求 URL、头或正文。回环连接绕过系统代理，连接限时，签名请求不重定向。
- MonOs 对通信失败的持久 pending_submission 每 30 秒最多探测一次正确世界的 `/readyz`；就绪后每个 event_id 最多提前续派一次。限额在 POST 前保存，复用原 event_id、idempotency_key、scheduled_job_id；失败后继续正常退避，重启不重置提前次数。取消、业务失败与未知执行不走该加速路径。
- 合并迟到激活快照时保存原计划的时间、理由、来源和分钟数，避免 retry 被改成 tool。原截止时间／退避保护继续保留。
- 新增回归发现 `bridge-repository.ts` 把 unknown/action_interrupted 映射为 failed。现在如实返回未知状态，MonOs 继续轮询原任务，不再从这一状态发起新提交。此项先失败、修复后通过。
