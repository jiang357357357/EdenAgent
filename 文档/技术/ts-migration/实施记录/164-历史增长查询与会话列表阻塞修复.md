# 历史增长查询与会话列表阻塞修复

日期：2026-10-04。承接客户单核跑满报告及两次启动截图，继续修复已定位的历史增长热点。本轮完成源码、旧库兼容和隔离联调，未修改客户数据库或便携包；截图中前一进程退出的原因仍缺少客户 MonPM 事件和退出记录，不能将本轮发现直接认定为那次重启的原因。

## 定位结果

1. 服务账号配置 MonOs 调度状态文件时，自醒发布每秒将全部 `self_awake_runs` 与实际 `agent.agent_start` 事件关联、聚合再排序，最后才 `LIMIT 1`。查询计划扫描全部自醒运行，每个运行按现有事件索引查找，并使用临时排序；不是扫描全部流式事件。临时库实测成本随自醒次数增长。
2. `session.context` 原查询每次对该会话全部 `model.request` 按角色分组。模型调用前的逐角色上下文查询，以及会话摘要对最近有效用量的查询，也可能倒查很长的请求/无用量响应历史。
3. 列表 RPC 原先同步逐个读取最多 1000 份会话摘要，中间没有 I/O 调度机会。健康接口自身读取内存，但与同步 SQLite 操作共用 Node 事件循环，因此仍会等待这些工作。

已有便携包的两份 `server/main.mjs` 还保留旧 Mon 同步和元数据查询；本轮修改开发源码不会自动更新客户正在运行的程序。SQLite ExperimentalWarning 本身不是崩溃证据。当前 MonPM 的独立 readiness 超时只改变就绪状态，不直接重启进程。

## 实施内容

### 自醒实际启动投影

迁移 129 增加 `self_awake_activations`，保存每次自醒运行真实 `agent.agent_start` 的最早时间，并索引最新时间。不能以派发时间 `self_awake_runs.started_at` 代替实际执行事实。事件写入与运行关联变化在同一事务中维护投影，覆盖事件先到、运行后关联、乱序时间、回滚及更新/删除。

发布端只取最新投影与对应运行的实时完成状态；无变化不写库、不改文件。历史清空后移除已无事实依据的 `agent_activation.json`，不删除其他 MonOs 文件。文件写失败保留数据库事实，由既有定时器重试。

### 请求和用量投影

迁移 130 增加逐会话/角色最新请求头和最近有效用量头。事件追加时原子维护最新序号；查询最多读取 32 个最新角色的请求，并按精确事件序号恢复原有完整正文。模型回调直接查该角色的上下文估算，不重新汇总其请求历史。用量继续沿用原有有效数值条件及 `modelContextUsage` 解释，不让无用量失败响应清空旧用量。

序号查询保留 SQLite INTEGER 与 BigInt 精度；模型数据损坏在所属会话读取时明确失败，不静默返回空结果，也不因无关流式正文损坏阻塞升级。历史修改/删除触发对应会话的投影重建。账号分区导入排除三张派生表，从获准导入的原始事件及自醒记录重建，防止复制源库行号或陈旧投影。

### 列表分批调度

新增 `SessionRepository.listAsync` 并接入生产 `session.list` RPC。初始让步后取得有序 ID 集合，每 25 条或累计 8 ms 让出事件循环，复用连接的 AbortSignal。筛选、顺序、数量上限及响应结构保持兼容，每条读取重新校验账号归属；期间删除或撤权使整次请求失败，不返回部分结果。

同步列表保留给已有内部调用。ID 筛选仍扫描/排序会话表，本次 3000 会话夹具耗时 3.677 ms；本轮没有声称消除了所有同步 SQL。

## 升级与剩余边界

- schema 129/130 是数据库版本，不推进产品版本；前 128 次迁移内容校验保持不变。首次打开旧库有一次性索引和投影回填成本，不能用上述小夹具时延推算客户 11 GB 库的升级时长。部署时应先验证客户副本；已升级库不能直接交给只支持旧 schema 的程序。
- 没有删除历史事件、自动 ANALYZE、放宽健康超时或降低持久化等级。仍使用同步 SQLite；磁盘锁等待、大正文恢复、其他业务负载不在“永不离线”的保证范围。
- 显式批量逐行修改/删除模型历史会触发反复重建，不宜当作批量清理接口。当前生产采用追加事件，旧转换仅调整元数据序号，未发现这种批量模型维护路径。
- 本轮未迁移真实数据库、重启用户服务、编译或替换客户包、提交或推送。客户截图两次启动的具体原因仍待现场退出记录确认；此次修复解决的是已能在源码和隔离夹具中定位的阻塞路径。
