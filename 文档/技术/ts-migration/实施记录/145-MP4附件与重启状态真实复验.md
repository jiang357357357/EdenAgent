# 145 MP4 附件与重启状态真实复验

日期：2026-09-25

## 范围

按用户要求进行真实测试。全部使用系统临时目录和临时 Core 身份服务，未把真实账号数据库作为测试夹具；测试后删除临时数据。使用当前工作区源码，不代表 Windows 已安装运行包的行为。

## 结果

- 用 FFmpeg 生成可播放的 1 秒、1545 字节 MP4。经真实 HTTP Blob 上传、WebSocket RPC 入队和记录模型执行，文件上传 200、输入 completed、消息含 `sample.mp4`，模型请求未收到视频字节；关闭并重新打开 Server 后消息仍在。
- 同一临时 Mon 账号上传该 MP4 返回 200，重启后 `accounts` 健康检查为 true。扩展到 33,554,433 字节后 HTTP 返回 413；MP4 不会直接造成所示账号初始化循环。
- 模型请求挂起时断开并重新连接前端 WebSocket，持久输入仍为 running、会话 executionStatus 为 busy；真正关闭再启动 Server，输入变为 interrupted、executionStatus 为 idle。另行模拟持久队列恢复：queued 继续执行到 completed，原 running 变为 interrupted，其后排队输入变为 held。
- 人为持有账号 `runtime-lock.db` 的排他锁，启动与后续请求重复出现 `account.import`、`account.services`，`server.account.failure` 指向 `account.services` 和 `Runtime data is locked or its ownership lock is unavailable`。这与截图的阶段序列相符，但不能单凭截图断定 Windows 原因。
- 人为将临时账号数据库版本设为宿主上限以上，失败停在 `account.import`，日志为 `Database schema is newer than this host`。因此此前将截图中 `account.services` 失败直接归因为数据库版本过高的判断不成立；旧版运行包仍是独立的待核对线索。
- 现有五组相关测试共 11 项通过：附件入队、附件 RPC、持久输入、账号传输和分区失败恢复。

## 待核对

需要 Windows 同一时段完整的 `server.account.failure` 行、实际运行包版本及 MP4 大小，才能确定该实例的账号初始化故障。前端读取文件前尚无 32 MiB 预检，较大 MP4 可能先被读为 Data URL，造成浏览器内存压力；本轮未在 Windows UI 实机复现。
