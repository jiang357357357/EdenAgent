# 工作区搬迁与账号启动恢复

日期：2026-10-03。范围：Workspace、账号启动、工作区 RPC、Web 资源管理器及 QQ 文件审批。用户明确要求修复后进行真实测试。

## 根因

错误报告中的便携目录从 `F:\EDEN` 搬到 `F:\EDEN(3)` 后，账号数据库仍保存旧的绝对 `workspace.root`。服务组装只在没有保存路径时设置默认工作区，技能与工具目录发现随后调用严格的 `workspace.root()`；`realpath` 的 ENOENT 因而升级成整个账号的 `account.services` 启动失败。

当前项目存在相同调用链。本次从工作区选择的持久化语义、启动依赖及用户恢复入口共同修复，不通过删除用户数据库配置处理。

## 实现与状态归属

| 模块 | 输入与输出 | 状态归属及失败行为 |
| --- | --- | --- |
| 工作区选择 | 启动默认位置、旧配置或显式选择 → managed/external 选择 | `WorkspaceRepository` 保存版本化 `workspace.selection`；保留迁移原因、旧值及最近路径变化证据 |
| 路径解析 | 逻辑选择 → 路径、类型及可用状态 | `WorkspaceLocation` 检查真实目录；返回 ready/missing/inaccessible/invalid/unselected，失效时仍保留原路径 |
| 账号启动及能力目录 | 已保存选择 → 可用账号与工具目录 | 可选目录发现只使用 `availableRoot()`；根路径不可用时不扫描项目技能，输出可恢复的结构化诊断 |
| 文件和终端执行 | 当前工作区、调用与审批 → 工具结果 | 严格 `root()/commandRoot()` 拒绝失效选择，执行前复核目录；不把失效选择当成未选择而回退用户 home |
| 工作区 RPC | 本账号会话及选择动作 → 新选择 | `workspace.switch`、`workspace.useDefault` 共用运行中回合检查；选择和事件同事务持久化，提交后广播 |
| Web 资源管理器 | 状态及用户操作 → 提示、目录或恢复 | 保留原路径与原因，提供重新读取、重新选择、回默认；只有 ready 才列目录，请求与结果受账号/世界 revision 保护 |
| QQ 文件审批 | 文件名及 canonical 工作区 → 审批后文件结果 | 审批详情绑定目录，审批结束后复核；目录失效或切换时不创建 blob/投递事件 |

默认工作区持久化为 `{version:1,kind:'managed',id:'default'}`，每次启动按当前账号数据根推导位置，因此复制或搬迁后即使旧目录仍存在，也使用当前安装的默认目录。显式项目路径持久化为 external。旧 `workspace.root` 仅保留为已有任务归属逻辑需要的兼容投影，不再作为 managed 的位置事实源。

旧配置只有与当前可验证的默认目录相同时才自动归为 managed；无法证明来源的旧路径按 external 保留，不根据 `workspace` 后缀猜测并切换。这类失效旧选择在升级后允许账号启动，由用户在资源管理器选择项目或点击“回到默认工作区”。迁移不会批量改写插件、技能、子任务或权限记录中的旧路径。

默认目录仅在首次账号初始化时自动创建。已经存在账号元数据时，重启不重建被删除的默认目录；用户显式回默认才可新建缺失的叶目录，祖先目录缺失、文件冲突或权限错误仍失败。恢复空目录不会找回被删除的原文件。配置路径不变但 junction 改向时保留原 canonical 绑定，跨重启也需显式重新选择；事务回滚后不会泄漏尚未提交的新绑定。

工作区恢复所需的审计会话直接通过 `session.create` 创建，不要求先配置模型或发送聊天消息。此次同时将 Sidebar 的工作区逻辑拆为状态控制器、提示及目录树组件。

## 验证环境与边界

全部验证使用 Windows、Node.js **22.23.1**、OS 临时目录、临时 SQLite 和本地测试服务。没有把真实用户数据库作为夹具，没有重启或替换运行中的用户服务，没有提交或推送。

真实运行链路使用生产 Server、HTTP、WebSocket、SQLite 和 PowerShell。对话测试的模型端是本地录制 HTTP 响应，不能等同真实供应商模型决策验收。前端验证执行生产状态控制器、客户端请求逻辑和 React SSR，没有完成可见浏览器或 Electron 的点击及视觉验收。未运行全项目全量测试。

本次隔离的是工作区根路径失效。根目录正常而项目技能目录损坏、无法读取或内容非法时，既有 `skills.start()` 仍可能使账号后台启动失败；没有把所有技能加载异常吞掉。`inaccessible` 有明确处理，但没有修改 Windows ACL 来单独制造真实访问拒绝。

宿主现有 OS 账户执行策略未改变；`protectedRoots` 在原 `workspaceRoot` 中即未执行重叠限制，本次不恢复已暂停的沙箱。QQ 路径绑定属于明确目录和审批期间切换的加固，不宣称复现了持久授权继承漏洞。
