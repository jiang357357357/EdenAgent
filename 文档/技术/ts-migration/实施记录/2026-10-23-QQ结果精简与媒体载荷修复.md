## 媒体保护、检查与恢复

- `packages/api/src/media-payload.ts` 定义媒体载荷边界：带类型/MIME 的图片、音频、文件等二进制字段，以及明确的 base64 字段，均不参与文字改写；文件说明等普通文字仍按其原有契约处理。纯文本中的 data URI/base64 URI 跨度也保持原样。
- QQ 投影及共用文字投影采用此边界，因此其他调用链不会因同值替换再次损坏图片。
- `packages/runtime-pi/src/checkpoint-images.ts` 对 SDK 消息、custom message 和压缩保留尾部里的图片执行严格编码检查。历史恢复和主/角色检查点保存均会检查；坏图不会静默写成新的有效检查点。
- 提供方请求在 payload hook 之后、HTTP 提交之前再次检查内嵌图片。无法恢复的坏图报出明确原因及重新提供图片的提示，不等待远端反复返回 400，不静默删图。
- 对损坏的 MCP 图片，按同一会话、工具名和 toolCallId 选择唯一原始操作回执；旧版本没有操作行时，可从 `agent.tool_execution_end` / `actor.runtime.tool_execution_end` 原始事件恢复。还核对图片数量、顺序、MIME 和原始编码。
- 原始记录缺失、调用/工具不匹配、记录歧义或原始编码无效时不猜测内容。不会把所有占位符替换成 `0`。恢复发生在模型副本中，读取本身不改写原检查点；后续正常运行可以保存已恢复的有效图片。
- 自动恢复目前覆盖有相应原始工具依据的 MCP 图片。缺少原始依据的用户附件仍需重新提供，不能无条件自愈。

恢复模块：`Server/src/modules/tool-results/{checkpoint-media,history-image-receipts}.ts`，由 `SessionRepository.restoreModelCheckpoint` 统一调用，角色检查点复用同一路径。正常检查点不查询额外旧图片事件；损坏调用按 ID 定位事件，避免拉取无关的大图事件。
