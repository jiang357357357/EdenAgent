## 已确认的原因与代码问题

### QQBot 离线，错误原因又被泛化

登录信息和好友列表两个原始回执明确说明 QQBot 未在线。Core 的 `Application/Domain/BOT/Core/napcat_actions.py` 在 `bot.status != "online"` 时返回此错误。能力目录查询成功只证明接口可提供操作目录；`list_contact_channels` 的 QQ `available=true` 也明确标注 `availabilityMeaning=configured_owner_target`，表示目标已配置，不表示机器人在线或能投递。

`Server/src/modules/mon/contact-delivery.ts` 将具体 Core HTTP 拒绝或失败响应统一改成 `Core rejected this contact`，私有投递记录也只留下 `Core rejected contact delivery`。因此直发请求已确认遭拒绝，但该请求本身的精确原始原因已丢失；不能仅凭通用错误把它断言为某个具体 HTTP 状态或权限问题。随后两次查询提供了当时 QQBot 离线的独立证据。

### QQ 业务失败被记为调用完成

`Server/src/modules/mon/napcat-tools.ts` 返回 NapCat 结构化回执，但未声明运行时的 `outcome` 映射。`packages/runtime-pi/src/tool-adapter.ts:45` 在工具没有声明映射时默认采用 `completed`，所以 HTTP／函数返回正常、正文 `status=failed` 的两次 QQ 调用被当作完成。

这是已确认的工具结果状态问题。应按 NapCat 自身契约区分成功、失败、未知及需选择目标等状态，保留原始审计结果，再向模型投影；不能对任意第三方结果统一按字段名猜测状态。

### 桌面后台投递不适用于这次 QQ 输入

03:51:58 的输入得到明确 `background_unavailable`。原生驱动契约对部分 Chromium／Electron 输入栈会拒绝后台字符投递，并要求明确升级到前台；当前结果与此契约一致。后续智能体确实请求了前台操作，但执行被暂停，不能把未完成的前台路径称为通过。

本次最后选择的控件角色为 `Text`、动作仅列 `text`，不是标准 `Edit`。这可能影响焦点建立，但现有回执没有足够证据证明控件选择错误；需结合实际窗口验证，不能将其作为已经确定的唯一根因。

### `unknown` 包含生效但未验证的动作

03:51:21 搜索框替换被记为 `unknown`，03:51:23 的观察已看到搜索词变成“店长”；03:51:27 选择结果被记为 `unknown`，03:51:29 的观察已看到 QQ 切换到“店长”会话。因此不能把所有 `unknown` 都当成未执行或允许直接重试。

`native-driver.ts` 将部分送达、无法验证和疑似无效果统一投影成相同提示，没有保留这些类别的具体区别和驱动原因。保守地保留未知结果合理，但现有证据不足以继续精确区分每次点击的不确定原因，应补充宿主私有回执与必要的模型说明，继续禁止未知输入自动重放。

### 暂停来源未记录，不能认定用户主动暂停或检测误判

`InputArbiter.control('pause')` 同时用于 UI 的手动暂停和物理输入接管检测，二者都生成“用户已暂停桌面控制”。现有控制状态只保存 `paused/stopped`，没有暂停原因和来源。

最后一次前台输入是在执行期间被暂停取消，但仅凭此消息无法判定是手动点击、真实硬件输入还是检测误判。此前未完成的硬件接管验收仍然有效；本轮遵守用户暂缓前台测试的指示，没有复现或重放现场。
