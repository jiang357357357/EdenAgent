# 空闲同步慢查询与单核占用修复

日期：2026-10-04。依据客户提供的《EDEN-agent-api-单核跑满-根因报告》，核查并修复 Agent 当前源码中的会话元数据和后台同步热点。本轮不访问客户数据库，不停止实际服务，不修改客户包，不推进产品版本。

## 问题与证据

报告定位到 Mon 同步器每两秒遍历已绑定会话：先完整执行 `SessionRepository.read()`，再判断重试时间和是否存在新增事件。元数据和标题来源的查询使用多个 `kind` 配合 `ORDER BY seq DESC LIMIT 1`；即使已有 `(session_id,kind,seq)` 索引，SQLite 仍可能为了满足排序选择 `(session_id,seq)`，从会话末尾扫描大量无关历史。

同步 SQLite 占用 Node 事件循环，因此即使没有 WebSocket 客户端，后台轮询也能拖慢 HTTP 健康接口。当前健康接口已经主要读取内存状态，仅改健康接口或放宽超时无法消除同步查询阻塞。此前流式写入合并、历史异步分页和语义投影筛选减少了其他路径的成本，没有覆盖这个元数据查询热点。

本轮先用包内 Node 22.23.1 / SQLite 3.51.3 和 12 万条合成事件做内存对照：连续 30 次双类型标题查询，默认计划 63.703 ms，强制已有复合索引 0.183 ms；该合成分布执行 `ANALYZE` 后仍选原计划，为 65.720 ms。新增 `seq DESC` 索引仍出现跨类型临时排序。此实验不是客户 877 万行数据库的复测，但证明不能将一次 `ANALYZE` 的效果推广为所有客户库的保证。

## 修复设计

1. 标题来源和会话元数据分别按单个事件类型查询最新一条，再用 BigInt 比较候选序号。复用现有索引，不增加冗余 DESC 索引，不依赖统计表存在，不丢失 INT64 序号精度。
2. 同步器先读取目标连接进度、退避时间及最新事件序号。无新增事件直接结束；仅有无关流事件时推进游标，避免完整会话读取。
3. 需要检查参与者和环境时使用轻量 `readMetadata`，不附带标题来源、模型用量和输入忙闲查询。继续检查会话所有权、运行域和删除状态；不按 `sessions.updated_at` 缓存完整会话，因为输入和模型响应变化不保证更新该字段。
4. 投影批次按类型读取有限序号候选，合并排序后仅加载最终批次的正文；投影更新时间也按类型取最新候选。保留投影顺序、增量游标、失败重试、已确认投递幂等、参与者配置等待及连接目标切换语义。
5. 会话扫描显式让出事件循环，让 HTTP/定时器有执行机会；不把 `await` 一个已完成 Promise 当成网络公平调度。

投影候选查询固定使用既有 `events_session_kind_seq`，只加载最终候选正文；该索引由现有迁移 110 创建。元数据查询通过精确类型等值和排序端点让已有索引完成定位。本轮不增加 schema 迁移，既有迁移/索引回归验证继续通过；不存在通过修改统计表伪造某种计划的步骤。

关联权限回归另发现既有 `rename()` 在完整读取校验前提交标题修改：跨账号调用虽然随后抛错，标题却已改变。本轮在写入前使用轻量读取完成所有权、运行域和删除状态检查，并验证拒绝请求不会改变标题或追加事件。此项是回归发现的独立缺陷，不将其当作本次 CPU 故障的原因。

不自动在启动主线程执行全库 `ANALYZE`。它在客户报告中耗时约 80 秒，且不能保证所有查询分布都变快。统计信息维护仍可在独立维护窗口进行，但本轮修复和回归必须在没有 `sqlite_stat1` 的条件下成立。SQLite 官方维护建议见 [ANALYZE / PRAGMA optimize](https://www.sqlite.org/lang_analyze.html)；`INDEXED BY` 是强制约束而非提示，见[官方说明](https://www.sqlite.org/lang_indexedby.html)。

最终复验结果如下。旧基线仅对两个热点会话执行三轮元数据/标题查询，共 12 条 SQL；不是完整旧同步器，因此不以该表计算端到端加速倍数。

三个空闲轮的完整会话、轻量元数据与投影批次调用均为零。新增流事件只进行一次必要批次查询，元数据读取仍为零，游标正确前进。完整机器数据、执行计划、第一次夹具 keepAlive 超时修正和最终复验见 [JSON 记录](../测试记录/2026-10-04-空闲同步百万事件.json)。短窗口 CPU 计时有系统粒度误差，不将其换算成长期 CPU 百分比。

回归还补齐：等待配置或背景会话只观察元数据序号；元数据损坏时单会话保留游标、进入退避，不中断后续健康会话。未跳过、删除或标记损坏事件为已投递。
