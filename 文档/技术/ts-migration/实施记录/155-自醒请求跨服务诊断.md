# 自醒请求跨服务诊断

日期：2026-09-27。范围：Agent Server `SelfAwakeHttp` / `SelfAwakeBridge` 与 MonOs `AgentClient`。

## 问题与边界

用户提供的 MonOs 画面显示 `/internal/self-awake/run` 返回 HTTP 400。旧 Agent Server 把请求解析、Core 服务身份、默认助手、模型目录和作业持久化等失败统一响应为 `Self-awake request could not be processed`；MonOs 使用 `error_for_status()` 后只保留 `HTTP 400 Bad Request`。因此旧截图无法证明具体失败原因，不能凭它判定是模型配置或签名问题。无凭据访问 `/internal/self-awake/status` 返回 403 属于预期的服务访问限制，与已签名的 run 请求要分开看。

## 修复

- Agent Server 对每个自醒 HTTP 请求生成 UUID，请求响应头使用 `x-eden-request-id`；错误 JSON 返回 `code`、`stage`、`requestId`，上游 HTTP 失败还返回 `upstreamStatus`。成功响应结构、签名算法、HTTP 状态规则保持原样。
- Server 在 `stderr` 记一行 `self_awake.request_failed` JSON，包含请求 ID、路由、HTTP 状态、阶段、固定错误码、错误类型，以及有界的上游状态、系统错误码、Schema 字段位置或源码栈位置。阶段覆盖请求体、签名、提交校验、身份、幂等、Core 服务令牌、助手、模型目录、会话与作业入库。异常文本、请求正文、令牌和签名均不写入诊断记录。准备失败后若清理空会话也失败，记录 `cleanupFailed`，但保留原始失败阶段。
- MonOs 的 run/status 调用读取最多 4 KiB 错误响应，仅提取格式受限的 `code`、`stage`、UUID 请求 ID 和上游状态。提交失败写入现有 `last_error`；状态轮询失败写入独立的 `last_status_error`，成功轮询清空它，不覆盖原有执行错误。两者均不保存原始响应正文。老版本 Agent 未返回诊断字段时仍记录 HTTP 状态并标记 `diagnostic unavailable`。

## 下次定位

先看 MonOs 状态中的 `last_error`（提交）或 `last_status_error`（轮询），例如 `Agent /internal/self-awake/run returned HTTP 400 (code=core_http_error, stage=assistant_fetch, request_id=..., upstream_status=401)`；再用 `request_id` 搜索 Agent Server 日志中的 `self_awake.request_failed`。若 `stage=submission_validation`，看 Server 日志的 `schemaIssues`；若 `code=unexpected_error`，看 `errorName`、`systemCode` 与 `stackFrames`。需要两端都运行包含本改动的版本，旧版历史 400 无法倒推原因。

## 验证边界

仅进行 Server TypeScript 类型检查、MonOs `cargo check --locked` 和静态差异检查；按当前项目实施要求未新增或运行自动化、冒烟或真实自醒测试，也未替换在线进程或访问真实用户数据库。真实线上下次失败仍需按请求 ID 核对两端日志。
