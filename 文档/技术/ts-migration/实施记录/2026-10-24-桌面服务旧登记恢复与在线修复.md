# 桌面服务旧登记恢复与在线修复

已修复旧版服务登记导致的永久连接阻塞，并恢复当前运行实例与 `eden.desktop.3` 共享桌面服务的连接。原有暂停状态保持不变；Electron 和两个 Agent Server 没有重启。本轮不执行 QQ、截图或键鼠操作，继续操作桌面前仍需用户在控制窗口恢复。

## 原因与复现

当前开发实例使用 `%TEMP%/EdenAgent/desktop-control`，残留 `eden.desktop.1` 登记，登记 PID 19108 已退出。客户端先读取协议字段并拒绝旧版本，尚未探测通信端点，因此把离线进程遗留的文件误当成仍在运行的旧服务；`connect(true)` 也无法进入启动逻辑。

原报错要求“结束旧共享服务并重新加载 Agent Server”，但托盘没有单独退出共享服务的入口。控制窗口的“停止”只改变操作状态，并不会退出服务进程。当前开发启动器还会在任一直属子进程退出时关闭整组受管进程，直接杀 Server 会影响客户端及其他服务。

开发启动器的环境白名单也遗漏了 `EDEN_AGENT_DESKTOP_BROKER_ROOT`，显式配置不能传给两个世界。本次只补传该配置，不改变未配置时的默认目录，避免把已有暂停状态留在旧目录。

## 实现

| 位置 | 行为 |
| --- | --- |
| `broker-connection.ts` | 先连接实际端点。只有 `ENOENT`／`ECONNREFUSED` 才判为离线；连接超时不证明服务不存在 |
| `broker-client.ts` | 离线且允许启动时启动内置服务。只读状态探测不启动、不删文件；状态探测与启动请求并发时，启动请求不会被离线结果吞掉 |
| `broker-registration.ts` | 新服务独占监听后，以完整临时文件原子发布登记；Windows 的 `EPERM`／`EACCES`／`EBUSY` 最多重试约 1 秒，不先删除旧登记 |
| `broker-process.ts` | 管理内置服务启动及启动错误，隐藏命令窗口，不按登记 PID 终止任何进程 |
| `desktop-broker.ts` 提示 | 活跃端点与登记版本不兼容时，说明需要通过启动器核对和协调升级，不再误导用户用“停止”退出服务 |

连接会等待监听后的短暂登记发布窗口，并校验认证回执确认为当前协议，不能把已附着但未认证的 socket 视为连接成功。已接收的业务调用在断线后保持未知，不自动重放。活跃旧版本、未来版本或无效登记均保留，不覆盖、不降级，也不启动竞争服务。

恢复不依赖 PID 是否仍存在，因此 PID 被无关进程复用也不会导致误杀或阻塞。`control.json` 不参与登记替换；暂停、停止和控制原因由现有 broker 逻辑读取。损坏的控制状态继续按原规则安全停止。

覆盖离线旧登记、PID 复用、只读探测、两世界并发恢复、监听先于登记、活跃旧版及未来版、损坏登记、认证等待与协议回执、启动失败、业务断线不重放，以及暂停文件逐字节保持。初次并发发布测试暴露 Windows `EPERM`，加入生产发布重试后通过。数据库夹具均为临时目录或内存库。

## 在线恢复

在确认旧端点离线后，使用已验证的新版 broker 更新同一目录的登记。首次连接复核记录在 `live-recovery.initial.json`；随后以隐藏的独立后台进程启动共享服务，跨调用确认存活，见 `live-recovery.json` 和 `process-liveness.json`。共享服务本身仍允许闲置回收，登记文件不能代替端点存活检查。

当前运行的尘世 Server 经正常鉴权 RPC 调用 `desktop.status`，由升级前报错恢复为可用、暂停、空闲。恢复前后 `control.json` SHA-256 完全一致。两个 Server 的 PID 67368／61132 和 Electron PID 74356 保持不变，没有中断现有聊天来重启整组服务。在线只切换共享 broker；Server 内存中的新版客户端恢复代码随下次正常重载进入，源码和构建已经完成。

本次没有解除暂停、发送消息、执行桌面输入或用真实用户数据库作为测试夹具。若恢复后仍为暂停，可从托盘打开“桌面控制”并点击“恢复”，随后重新发现和观察目标；恢复不会重放先前失败的动作。
