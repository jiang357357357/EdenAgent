# 开发启动与 MonPM 端口冲突修复（2026-10-18）

本记录针对用户在 01:55 看到 Agent 与 Vite 就绪、随后回到 PowerShell 的问题。时间均为 Asia/Shanghai；这是开发启动链路验收，不是全部业务、安装包或整机重启验收。

## 真实原因

日志的“账号已就绪”“服务已就绪”和 Vite ready 都是正常启动信息，单凭这几行不能确认进程后来为什么退出。现场只剩 MonPM 持有的伊甸园和 MonOs，40091／40093 没有监听，Agent 桌面也不在。

| 01:54:55 | 原 MonPM Agent 退出，触发自动重启 |
| 01:54:59 | MonPM 新包装进程启动 |
| 01:55:01 | 用户日志中的开发 Agent 与 Vite 就绪 |
| 01:55:05 | MonPM stderr 报 Runtime data is locked or its ownership lock is unavailable |
| 01:55:06 | MonPM 再次因进程退出进入重试 |
| 01:55:09 | MonPM port_cleanup 明确记录结束 40092 上的 PID 55108 |
| 01:55:11 | MonPM 自己的 Agent 再次启动，后续恢复 healthy/ready |

旧 `dev.mjs` 无条件调用 `takeOverTcpPort` 结束 40092 监听。Windows 的该实现没有像 Linux 分支那样停止对应 MonPM 所有者；MonPM 的 running 期望保持不变，随后重启并结束竞争者。开发启动器又在任何自有子进程退出时关闭其余子进程，而且原先没有具体退出日志，所以用户只看见“启动成功”后返回提示符。

10-17 已使 MonPM 常驻并验证自醒通信恢复，但没有覆盖默认开发入口与受管服务并存；此前运行的是专门的 `dev:desktop` 路径。本轮修复默认入口，保留常驻所有权。

## 实现

- `Script/Project/development-realm.mjs` 核对既有 Agent 的健康响应、世界、版本与工作区，读取所配置逐世界令牌文件并进行真实 WebSocket 能力握手。握手后立即关闭，不初始化账号、不提交输入、不调用业务 RPC；身份不匹配时不发送令牌。
- 完全空闲的后端端口才允许创建新进程；监听但无有效健康响应、身份不符、令牌缺失／不接受时明确报错，保留原进程。Web 端口占用也直接报错，防止结束另一开发组后间接带走准备复用的 Server。
- `dev.mjs` 为外部服务传递原令牌和令牌文件，不轮换凭据，不把它加入 children；shutdown 只关闭自己创建的进程。子进程退出记录标签、code 和 signal，避免无说明返回。
- 新增 IPC shutdown，供实际 CLI 联调或父启动器有序结束所拥有的进程。普通 Ctrl+C／SIGTERM 路径继续存在。
- `packages/api` 导出窄入口 `@eden/api/rpc`，启动器从协议来源取得握手常量。这样避免复制协议值，也避免普通 Node 22 脚本加载完整 API 图时遇到不支持直接去类型的 TS 参数属性。
- 更新根 `test:project`、运行文档与脚本说明。显式接管工具仍保留给其他入口；本轮没有重写 MonPM、改变自动重启策略或清空数据锁。

复用的后台进程不会因前台构建完成而自动加载新的后端源码。需要升级后台业务实现时，仍应通过其原监管器重启；本轮只修改启动链路，不需要重启现有 Agent。
